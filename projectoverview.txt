# VirusWatch — Project README & Development Handover

**Project:** VirusWatch  
**Platform:** AI-assisted infectious-disease surveillance, trend analysis, and research support  
**Primary geographic focus:** Pakistan, especially Sindh and Karachi where source data supports that level of detail  
**International scope:** Selected international surveillance comparisons where data is genuinely comparable.

**Purpose of this document:** Preserve the project vision, technical architecture, frontend and backend requirements, research direction, data inventory, development progress, and outstanding tasks so development can continue in another cloud-agent account without losing important context.

---

# 1. Project Overview

## 1.1 What is VirusWatch?

VirusWatch is an AI-assisted infectious-disease surveillance and trend-analysis platform designed to bring together official disease surveillance data, public-health reports, and scientific research.

The platform will help users explore disease patterns, monitor changes over time, examine geographic distributions, identify unusual trends, and access research evidence through an AI Research Assistant.

The initial focus is Pakistan, particularly Sindh and Karachi where reliable district-level data is available. Selected international sources will provide additional context and comparison.

VirusWatch is intended to support public-health research and surveillance. It is not a diagnostic tool and must not replace public-health authorities.

## 1.2 Main Project Objectives

The main objectives are:

1. Collect infectious-disease surveillance data from official and trusted sources.
2. Integrate Pakistan's public-health surveillance reports.
3. Integrate selected international surveillance datasets.
4. Monitor disease trends over time.
5. Analyze geographic patterns at the resolution supported by the data.
6. Identify possible anomalies and unusual changes.
7. Provide an AI-powered research assistant using scientific literature and approved data.
8. Generate research summaries and surveillance reports.
9. Provide notifications about source updates and possible surveillance signals.
10. Maintain transparent data provenance, source attribution, and reporting limitations.

## 1.3 Important Principles

VirusWatch must follow these principles:

- Never fabricate disease statistics or surveillance observations.
- Never present synthetic testing data as real surveillance data.
- Preserve missing, suppressed, not-reported, and zero values as different states.
- Display the source, reporting period, unit, and data freshness.
- Do not combine incompatible surveillance indicators.
- Do not infer district-level data from provincial totals.
- Treat anomaly detection as an early-warning screening mechanism, not confirmation of an outbreak.
- Preserve historical corrections and data revisions.
- Keep private API keys and credentials on the backend.
- Make all important results traceable to their original data or research source.

VirusWatch has two main development environments.

## 2.1 Lovable — Frontend Development

Lovable is responsible for building the user-facing application.

**Frontend technology:**
- React
- TypeScript
- Tailwind CSS
- Recharts or an equivalent charting library
- Supabase Auth if configured

Lovable handles:
- Dashboard design
- Navigation and pages
- Charts and visualizations
- Tables and filters
- Geographic visualization
- AI assistant interface
- Reports and research interface
- Notifications
- User settings
- Administration interface
- API integration with the backend

Lovable should not invent surveillance statistics, perform independent official disease calculations, or expose private API credentials.

## 2.2 Cloud Agent — Backend Development

The cloud agent is responsible for the backend, data processing, APIs, database, and AI functionality.

**Backend technology:**

| Component | Technology |
|---|---|
| Backend framework | Python, FastAPI |
| Validation | Pydantic |
| HTTP requests | HTTPX |
| Data processing | Pandas |
| Database access | SQLAlchemy |
| Database | Supabase PostgreSQL |
| Authentication | Supabase Auth |
| Database security | PostgreSQL RLS |
| File storage | Supabase Storage |
| Vector support | pgvector |
| Research retrieval | LangChain |
| AI workflows | LangGraph |
| Language model | Gemini |
| Email | Resend |
| Testing | Pytest |
| Code quality | Ruff |

The backend is the source of truth for surveillance data and analysis.

**Important:** Do not add unnecessary infrastructure such as MongoDB, Redis, Celery, separate vector databases, or additional AI agents unless a clear technical requirement justifies it.

# 7. Research Component and Scientific Direction

VirusWatch should support both surveillance analysis and scientific literature review.

Potential research questions include:

- What seasonal patterns are visible in Pakistan's influenza laboratory surveillance?
- How do influenza positivity and subtype patterns change over time?
- What trends are visible in NIH weekly suspected-case bulletins?
- Which diseases show unusual changes requiring further investigation?
- How do Pakistan surveillance indicators compare with selected international indicators?
- How do reporting delays, missing weeks, testing volume, and geographic coverage affect interpretation?

These are research questions, not established findings.

## 7.1 Research Assistant Workflow

The planned workflow is:

1. Register each research document.
2. Extract text and tables.
3. Preserve page numbers and section context.
4. Clean headers and footers.
5. Divide documents into meaningful chunks.
6. Store document metadata with every chunk.
7. Generate embeddings.
8. Store embeddings in the configured database/vector extension where enabled.
9. Retrieve relevant passages for a user question.
10. Generate an answer through Gemini on the backend.
11. Cite the relevant document and page/section where possible.
12. Report when the available evidence does not answer the question.

Each document should have metadata such as:
- Title.
- Authors.
- Journal.
- Publication year.
- DOI or URL.
- File checksum.
- Licence/access status.
- Processing status.

## 7.2 Research Evaluation

Before making strong claims, evaluate:

- Parser accuracy.
- Data completeness.
- Data-source coverage.
- Ingestion reliability.
- Duplicate and correction handling.
- Anomaly precision and recall.
- False-alarm rate.
- RAG retrieval relevance.
- Citation correctness.
- AI answer faithfulness.
- Unsupported-claim frequency.

Do not claim that VirusWatch predicts outbreaks or has validated anomaly-detection accuracy until appropriate evaluation has been conducted.

# 8. Automated Data Synchronization

A manual ingestion command is not the same as automatic synchronization.

## 8.1 Required Behaviour

VirusWatch should periodically check official data sources according to their publication schedules.

When a new or revised dataset is available, the system should:

1. Check the official source.
2. Detect a new or updated release.
3. Download the dataset automatically.
4. Record retrieval metadata.
5. Preserve the original file where permitted.
6. Parse and validate the data.
7. Normalize it to the canonical database schema.
8. Prevent duplicate records.
9. Preserve corrected records and revision history.
10. Commit valid updates safely.
11. Log failed attempts and rejected records.
12. Retain the last good dataset if a new retrieval or parsing attempt fails.
13. Update source freshness information.
14. Display the last successful synchronization time on the dashboard.

A source check that finds no new release is a successful check, not a failed download.

A weekly bulletin should only be expected after it has been published.

## 8.2 Synchronization Status

Keep these states separate:

- Last checked.
- Last successful download.
- Last successful ingestion.
- Latest reporting period.
- Latest publication date, if known.
- Current source status.
- Number of records accepted/rejected.
- Most recent error, if any.

Scheduled polling does not make a weekly source live or real-time.

**Important:** Do not claim automatic synchronization is implemented until an actual scheduler/job and end-to-end tests exist.

### Critical Data Rules

1. WHO FluNet is laboratory virological surveillance, not total clinical influenza cases.
2. NIH bulletins may report suspected cases; preserve the source definition.
3. Preserve `NR` and missing values as missing, not zero.
4. CDC ILINet %ILI and NREVSS %positive are different indicators.
5. Measles wastewater data has multiple units and assay variants. Never combine incompatible measurements.
6. Wastewater measurements are not clinical case counts.
7. Facility and general health-indicator datasets are contextual data, not active disease surveillance.
8. Never infer district values from provincial totals.
9. Never label a possible anomaly as a confirmed outbreak.
10. Preserve source attribution, units, reporting periods, missingness, and historical revisions.
